# What the TinyCC junction's i386 stages ask of a kernel

Measured 2026-11-20 on route/tinycc 05860bb, from one run of
`tests/tinycc/junction-check.sh` (which ended at live-bootstrap's
`/usr/bin/tcc` `b9dce87d…` and the six libraries) under `strace -n -f`.
This is the list a kernel has to serve for the junction's compilers.

## How it was measured

A `bwrap` wrapper earlier in `PATH` ran the real bwrap under strace, so
every process in the chroot was traced:

```sh
mkdir -p /tmp/t/bin
cat > /tmp/t/bin/bwrap <<'EOF'
#!/bin/sh
exec strace -n -f -s 200 -v -o /tmp/t/trace.$$ /usr/bin/bwrap "$@"
EOF
chmod +x /tmp/t/bin/bwrap
PATH=/tmp/t/bin:$PATH tests/tinycc/junction-check.sh
python3 kernel/k1/tests/i386-trace.py "$(ls -S /tmp/t/trace.* | head -1)"
```

(The smaller trace file is the `--probe` run.)  For the five compilers'
processes every trace line parsed as a complete call: no unfinished or
resumed lines, nothing skipped.  strace 7.3 decodes each
call with the process's own table, so the numbers below are i386 numbers
for the i386 programs and x86-64 numbers for tcc-mes.
`kernel/k1/tests/i386-trace.py` attributes each call to the program the
process last exec'd and does not count the execve that started it, which
is the parent's call.

## The i386 programs

28 processes: tcc-boot0 9 runs, tcc-boot1 9, tcc-boot2 8, tcc (the copy
of tcc-boot2) 2.  24,787 calls.  Ten distinct system calls:

| i386 nr | call | boot0 | boot1 | boot2 | tcc | how it is used |
|---:|---|---:|---:|---:|---:|---|
| 45 | brk | 9,944 | 9,944 | 1,447 | 255 | mes `malloc`: one `brk(0)` per run, then one `brk(cur+size)` per allocation, never shrinking; only a return of -1 counts as failure |
| 3 | read | 400 | 400 | 143 | 24 | regular files only; nothing reads stdin |
| 4 | write | 313 | 313 | 229 | 29 | fd 1 and 2 one byte at a time (mes `eputs`), files in blocks |
| 5 | open | 257 | 257 | 173 | 15 | see the flags below |
| 6 | close | 118 | 118 | 63 | 15 | |
| 19 | lseek | 116 | 116 | 24 | 12 | SEEK_SET, SEEK_CUR (also with -60), SEEK_END; every offset under 2 GiB |
| 1 | exit | 9 | 9 | 8 | 2 | always status 0; `exit`, not `exit_group` |
| 10 | unlink | 8 | 8 | 7 | 2 | objects and `*.a.tmp`; ENOENT is expected: the runs that write `tcc-boot1` and `tcc-boot2` unlink them first |
| 195 | stat64 | 2 | 2 | 2 | 1 | only from mes `remove()` on tcc's `ar` temporary `*.a.tmp`: it tests `S_ISDIR(st_mode)` and then unlinks |
| 183 | getcwd | 1 | 1 | 0 | 0 | the `-g` compiles of tcc.c (boot0 building boot1, boot1 building boot2); buffer 512, returned 50 |

Arguments, exactly as seen:

- `open`: `O_RDONLY` (including 139 failed include-path probes per
  compile of tcc.c, which must fail with ENOENT); `O_WRONLY|O_CREAT|O_TRUNC`
  with 0666 (objects), 0777 (the executable) and 0600 (the `.a`
  archives); `O_RDWR|O_CREAT` with 0600 (`ar`'s `fopen(tfile, "wb+")` on
  `*.a.tmp`, which the previous `ar` removed; written, then read back
  after `lseek` to 0).  The flag values are the x86-64 ones
  (`O_CREAT` 0x40, `O_TRUNC` 0x200), so no flag translation is needed.
  Paths are relative (225 of the 267 path arguments of open, unlink and
  stat64 across the boot0 runs) and absolute; none contains `..`, `/./` or `//`.
- File descriptors never go above 8.
- `getcwd` returns `/steps/tcc-0.9.26/build/tcc-0.9.26-1147-gee75a10c`,
  and the string goes into the `-g` stabs of tcc-boot1 and tcc-boot2.  A
  kernel must lay the tree out at that absolute path or `d9116def…` and
  `b9dce87d…` are not reached.  mes `_getcwd` only checks `r >= 0`.
- `stat64` fills a 96-byte i386 `struct stat64`; only `st_mode` is read:
  tcc-boot0's `remove` passes a 0x60-byte buffer at -0x60(%ebp) and
  tests the dword at -0x50(%ebp), offset 16, against 0xf000/0x4000.
- Peak heap growth from `brk(0)`: 18.5 MiB (0x12860ac) for boot0 and
  boot1 compiling tcc.c, 3.1 MiB for boot2, 2.5 MiB for `tcc`.  The
  initial break may be anywhere above the image (Linux randomised it;
  it was above 128 MiB in every run here).
- No `mmap`/`mmap2`, `ioctl`, `fstat`, `access`, `rename`, `chdir`,
  `fork`/`clone`/`vfork`, `execve`, `waitpid`, signals,
  `set_thread_area` or `exit_group`.  The i386 programs never start
  another program: the script driver does that.
- Floating point: `-D HAVE_FLOAT=1` builds use x87 code, so the FPU state
  must survive a context switch (K1's FXSAVE covers it).

## The ELF32 files

`tcc-boot0`, `tcc-boot1` and `tcc` (readelf):

- ELF32, `ET_EXEC`, `EM_386`, static: no `PT_INTERP`, `PT_DYNAMIC`,
  `PT_GNU_STACK` or TLS.  Two program headers, both `PT_LOAD`, align
  0x1000:
  - text, R E: offset 0, vaddr 0x08048000, filesz = memsz 0x375a4
    (boot0) to 0x37890 (boot1);
  - data, RW: offset 0x375a4…, vaddr 0x080805a4… (vaddr ≡ offset mod
    4096), filesz 0x6ab0, memsz 0x1a4d0 (0x13a20 of bss).
  The two never share a page.  The image ends below 0x080a0000.
- Entry 0x08048074, just past the ELF header and the two program headers.
- Entry stack: mes `crt1.c`'s `_start` is compiled by tcc, so it starts
  with `push %ebp; mov %esp,%ebp`, then reads argc at `4(%ebp)`, argv at
  `ebp+8` and envp at `ebp+4*(argc+3)`.  That is the Linux i386 layout in
  4-byte words: argc, argv[], NULL, envp[], NULL.  No auxv is read and no
  register is read at entry.  The largest command line was 49 arguments,
  1,093 bytes with the environment's 20 strings.
- System call convention: `int $0x80`, number in eax, arguments in ebx,
  ecx, edx (no call here takes more than three; esi, edi and ebp are never
  used), result or -errno in eax.

## The x86-64 side

The first tcc (`build-out/tinycc/tcc-first`, run as `tcc-mes`): 11 runs,
728,266 calls, seven distinct (x86-64 numbers):

| nr | call | count | how |
|---:|---|---:|---|
| 1 | write | 727,345 | 727,160 of them one byte to a file: pnut's `fputc` does not buffer |
| 0 | read | 431 | files |
| 2 | open | 272 | `O_RDONLY` (139 ENOENT probes), `O_WRONLY\|O_CREAT\|O_TRUNC` 0666/0777, `O_RDWR\|O_CREAT\|O_TRUNC` 0666 |
| 3 | close | 133 | |
| 8 | lseek | 64 | SET, CUR, END |
| 60 | exit | 11 | status 0 |
| 87 | unlink | 10 | 5 ENOENT |

No `brk`, `mmap` or `getcwd`: its heap is in its own bss (one RWX
`PT_LOAD` at 0x400000, filesz 0xc0f70, memsz 0x19e5048, entry 0x400078).
Building it (`./seed-forth` reading the layers, `tinycc/tcc-compile.fth`
and `direct-input.c`) uses `open` (90), `read`, `close`, three anonymous
`mmap`s (2, 8 and 9 MiB), one 790,384-byte `write` and `exit`.

That first tcc was pnut's libc's (`7b2efd95…`).  Since route/tinycc's
merge it has Mes libc (`d9e97270…`): its malloc grows the heap with `brk`
(at most 19.5 MiB from `brk(0)` over the junction's 11 runs, measured with
strace) and its `remove` calls `stat` (3 calls, tcc -ar's `.tmp` file).
K0 gained `brk`; without `stat` the `.tmp` files stay, outside boot 2's
stream.

K1 already serves all of these, and so does K0 (`kernel/k0/k0.asm`: read,
write, open, close, lseek, mmap, unlink, exit).  K1 also already has
`getcwd` (x86-64 79, `path_of` in `fs.c`), so the only new handler the
i386 list needs is `stat64`'s i386 layout.

What runs the script is a separate question.  On the host it is bash with
coreutils, gzip, tar and python3 (`tinycc/kaem-shims.sh`).  In a guest it
needs a kaem and the tools pass1.kaem names: `catm`, `match`, `mkdir`,
`cp`, `chmod`, `rm`, `sha256sum`, `ungz`, `untar`, `simple-patch`,
`checksum-transcriber`.  K1 runs kaem and the stage0-posix tools today,
built by seed-cc (`kernel/k1/direct-smoke.recipe`).

## Summary

A kernel that runs the junction's i386 stages needs: `int 0x80` with the
ten calls exit 1, read 3, write 4, open 5, close 6, unlink 10, lseek 19,
brk 45, getcwd 183 and stat64 195; a loader for a two-segment static
ELF32 at 0x08048000; a Linux i386 argv/envp stack; and the files at the
paths live-bootstrap uses.
